# Hamlet HQ — homeowner mockup

An interactive, clickable mockup of the **🏠 Homeowner (owner-occupant)** app from the
[Phase 1 specification](../docs/). Every screen is real React Native, every interaction
works, and every piece of data comes from an in-memory fake backend — no server, no
network, no accounts.

> **Scope is deliberately one persona.** There is no board member, community manager,
> executive, platform admin or auditor surface here. Those are different apps with
> different risks, and mixing them into a homeowner mockup would misrepresent the shape
> of the product.

## 📱 Getting it onto an Android phone

Three routes, fastest first. **Option A needs nothing installed on your machine except
Node.** Option B produces a real installable `.apk` in the cloud. Option C builds it
locally and needs the Android SDK.

### Prerequisites for all routes

```bash
cd mockup
npm install
```

Node 20 or newer. Check with `node -v`.

---

### Option A — Expo Go (fastest, ~2 minutes, no build)

Good for a first look. Everything in this mockup runs inside Expo Go.

1. Install **Expo Go** from the Play Store on your phone.
2. On your machine:

   ```bash
   cd mockup
   npx expo start
   ```

3. Make sure the phone and the computer are on the same Wi-Fi, then scan the QR code
   from the terminal with Expo Go.

   Behind a restrictive network, force a tunnel instead:

   ```bash
   npx expo start --tunnel
   ```

The app reloads as you edit. This is not an installed app — it lives inside Expo Go and
disappears when you stop the dev server.

---

### Option B — Build a real `.apk` with EAS (recommended)

Builds on Expo's servers, so you do **not** need Android Studio, the SDK, or a JDK.
Requires a free Expo account and about 10–15 minutes for the first build.

```bash
# 1. Install the CLI (once)
npm install -g eas-cli

# 2. Sign in (create a free account at expo.dev if you don't have one)
eas login

# 3. Link this project to your Expo account.
#    Writes an `extra.eas.projectId` into app.json — commit that change.
cd mockup
eas init

# 4. Build an installable APK
eas build --platform android --profile preview
```

The `preview` profile in [`eas.json`](./eas.json) is already set to
`buildType: "apk"` — that matters, because EAS defaults to an `.aab` App Bundle, which
you **cannot** sideload onto a phone.

When the build finishes the CLI prints a URL and a QR code:

- **From the phone:** scan the QR code, tap the download, then open the file.
- **From the computer:** download the `.apk`, then
  `adb install -r ~/Downloads/hamlet-hq-mockup.apk`.

Android will ask you to allow installs from your browser or file manager the first time
— **Settings → Apps → Special app access → Install unknown apps**. This is expected for
any app not coming from the Play Store.

EAS generates and stores an upload keystore for you on the first build; accept the
prompt. Later builds reuse it.

#### Rebuilding after changes

```bash
eas build --platform android --profile preview
```

Bump `expo.version` in `app.json` when you want a visibly different version; with
`appVersionSource: "remote"` the Android `versionCode` is incremented by EAS for you.

---

### Option C — Build locally

Needs **JDK 17** and the **Android SDK** (Android Studio, or `sdkmanager` with platform
tools + build tools). Set `ANDROID_HOME` and put `platform-tools` on your `PATH`.

```bash
cd mockup

# Generate the native android/ project (it is gitignored — this is expected)
npx expo prebuild --platform android --clean

# Either: build and launch straight onto an attached device
npx expo run:android --variant release

# Or: build the APK and install it yourself
cd android
./gradlew assembleRelease
adb install -r app/build/outputs/apk/release/app-release.apk
```

The APK lands at `android/app/build/outputs/apk/release/app-release.apk`.

**Note on signing:** the generated project signs the release build with the standard
Android debug keystore. That is fine for sideloading onto your own phone and *not* fine
for the Play Store — a store release needs its own upload key, which is exactly what EAS
manages for you in Option B.

**Never hand-edit `android/`** — it is generated, gitignored, and regenerated by
`expo prebuild`. Configuration belongs in `app.json` or a config plugin.

### Troubleshooting

| Symptom | Fix |
|---|---|
| `adb: no devices/emulators found` | Enable Developer Options → USB debugging on the phone, then `adb devices` and accept the prompt on the phone. |
| "App not installed" on the phone | An older copy with the same package is already there — uninstall `app.hamlethq.mockup` first. |
| EAS build fails at "Install dependencies" | Delete `package-lock.json` and `node_modules`, run `npm install`, commit the fresh lockfile, rebuild. |
| Metro cannot connect from the phone | `npx expo start --tunnel`. |
| Fonts or icons missing after a bare install | `npx expo start -c` to clear the Metro cache. |

## What the mockup covers

Every homeowner-facing Phase 1 requirement, wired end to end:

| Area | What works |
|---|---|
| **Identity** | Email + password sign-in, SMS one-time-code path, session in `expo-secure-store`, profile edit, sign out |
| **Amenities** | Six bookable spaces, real-time availability grid, conflict prevention, duration and guest limits, lead-time and weekly-quota rules, recurring weekly bookings, waitlists, cancellation |
| **Payments** | Itemised balance, per-charge selection, ACH vs card with a pass-through convenience fee, receipts, autopay, payment methods, full ledger |
| **Documents** | Full-text search across bodies, category filters, version history, e-signature acknowledgment |
| **Violations** | Notices with photo evidence, cure countdown, structured dispute, fine payment that closes the violation |
| **Architectural review** | Submit an ARC application with attachments, track it through a status timeline |
| **Service requests** | Report an issue by category, priority and location; track its progress |
| **Elections** | Multi-seat ballots and referenda, eligibility check, anonymised vote with a receipt, live turnout, quorum, closed-ballot results |
| **Inbox** | Board announcements and direct messages, unread state, threaded replies |
| **Directories** | Opt-in owner directory with field-level privacy, service directory of neighbours and vetted providers |
| **AI assistant** | Grounded Q&A over this community's own documents, with source citations that open the document |
| **Notifications** | Channel and per-category preferences |

### What is deliberately fake

- **No server.** `src/mock/` is an in-memory store that resets on reload. Booking rules,
  quotas and conflict checks are enforced there so the UI cannot lie about them.
- **No payment processor.** Nothing is charged. See the 🔴 notes below.
- **No AI model.** The assistant does keyword retrieval over a hand-written knowledge
  base in `src/features/assistant/knowledge.ts` and refuses anything it cannot cite.
- **No photographs.** Amenity tiles and evidence photos are lime gradients with glyphs.
  A mockup with realistic faces and property photos reads as a real product, which it is
  not.

### 🔴 Tier 3 — do not treat as a reference implementation

`src/features/auth/*` and `src/features/payments/*` are **drafts for a mockup**. They
have no server, no signature verification, no idempotency, no webhook reconciliation and
no audit trail. `src/features/payments/api.ts` lists, in a comment, the failure modes a
real implementation must answer for: double-submit, partial failure, retry-without-
recharge, wrong user, malformed input. Rewrite both from scratch against Supabase and
Stripe, and review them line by line.

The same applies to the election flow: ballot secrecy is modelled (the store keeps
"this unit voted" and never the selection), but there is no tamper-evident audit trail.

## Layout

```
mockup/
├── app/                      # routes only — screens compose hooks and components
│   ├── _layout.tsx           # providers, splash animation, auth redirect
│   ├── sign-in.tsx
│   ├── (tabs)/               # Home · Book · Pay · Inbox · More
│   ├── amenity/[id].tsx      # availability grid + booking flow
│   ├── checkout.tsx          # 🔴 payments
│   ├── documents/            # search, detail, e-signature
│   ├── elections/            # ballots and results
│   ├── violations/           # notices and disputes
│   ├── arc/  requests/       # architectural + service requests
│   └── assistant.tsx         # grounded Q&A
├── src/
│   ├── components/           # app-level shared UI
│   │   └── ui/               # primitives — check here before creating anything
│   ├── features/<slice>/     # api · keys · hooks · schemas · types · utils · components
│   ├── lib/                  # cn, format, fees, theme tokens, storage, query client
│   └── mock/                 # the fake backend: types, seed, rules
├── global.css                # design tokens (lime + pure-white, cool neutrals)
└── tailwind.config.js
```

Cross-feature imports go through a slice's `index.ts`, never a deep path.

## Design notes

- **Lime green is the only brand hue** — deep and saturated (`hsl(84 80% 33%)`), never
  neon. It carries the balance card, primary actions, the tab pill and selection states.
- **The ground is pure `#FFFFFF`.** Every neutral is cool (hue ~220) so nothing next to
  the lime reads beige.
- **No hardcoded colours in components** — semantic classes only (`bg-background`,
  `text-muted-foreground`, `border-border`). The handful of places that need a raw
  string (gradients, SVG fills, icon tints) read named values from `src/lib/theme.ts`.
- **Motion is on the UI thread.** Reanimated drives the tab pill, the segmented control,
  the counting balance, the success checkmark and every press. Nothing animates through
  React state.
- **The mockup is locked to light** (`userInterfaceStyle: "light"`) because the brief
  calls for a clean white ground. Dark tokens are still defined in `global.css` so a
  future dark mode has somewhere to land.

## Not verified

This was built in a headless container with no Android SDK, no emulator and no iOS
toolchain. **It has not been run on a device or simulator.** What *has* been verified:
`npm run verify` passes (typecheck, lint, 65 unit tests) and the Android bundle exports
cleanly via `npx expo export --platform android`. Layout, animation timing and gesture
feel need a real screen before anyone calls them done.
